## 一、优点

### 1.1 因果链视角，能发现单点审查遗漏的级联问题

传统 bug 审计往往是"逐文件扫错误"，容易把每个问题当孤立点处理。本次审计以因果链为轴线，沿 FLAG 写入点 → 门控判定 → 纪元推进 → 下游消费的完整路径追踪，**能发现级联失效**。

典型案例：AR-1（`eto_founded` 不可达）。表面看只是一个 FLAG 写不进去，但沿因果链追踪发现它级联影响 3 个人物解锁（伊文斯/林云/章北海），进而导致这 3 人在后续纪元的 filteredEvent 全部失效，最终影响 BUNKER 及之后所有纪元的可达性（AR-20）。单点审查最多发现"FLAG 没写进去"，因果链审计能追到"FLAG 没写进去 → 人物不解锁 → 死后发言 → 纪元不可达"的完整崩溃链。

**学习价值**：审计的轴不是文件，而是"状态如何流动"。这迫使审计者把代码当成一个有生命周期的系统来看，而不是一堆静态文本。

### 1.2 分层证据体系，强制每个结论有代码锚点

五级证据等级（已确认/有证据支持/推断/未确认/证据冲突）看似啰嗦，实际是**反臆断机制**。任何"我觉得这里有 bug"的直觉，必须落到具体行号才能升级为"已确认"。

BASELINE 阶段甚至明确写了"未正式审计任何纪元，未输出缺陷结论"——这种克制很重要。基线阶段登记了 12 项证据冲突和 12 项未确认项，但全部标注"仅登记不判定"，把判定权留给后续有完整证据的阶段。

**学习价值**：审计最大的敌人不是代码复杂，而是审计者自己的"看走眼"。证据分级强迫你区分"我看到了"和"我推断的"，防止推断被当成事实传播。

### 1.3 接口审查机制，专门捕获跨纪元断裂

单纪元审计天然有个盲区：每个纪元都觉得自己没问题，但拼起来断了。本次审计设计了"相邻纪元交接由主审统一核对"的机制，每个纪元审计报告末尾都带"下游接口审查项"交给下一个纪元核验。

正是这个机制发现了 AR-20：BROADCAST 纪元审计时发现 `bunker_world_completed` 的 epoch 标注错误（SYS-1 循环依赖），导致 BUNKER 及之后所有纪元在正常路径下不可达。如果没有接口审查，BUNKER 纪元审计会独自"看起来正常"（因为它假设入口 FLAG 已设置），而发现不了入口根本不会被设置。

**学习价值**：模块化审计必须配接口审查。每个模块自证清白不够，要证明"我假设的上游条件真的会被满足"。

### 1.4 子代理"只取证不判定"，隔离判定偏差

本次审计用子代理并行取证，规则是"只取证不判定；任务具体可证伪；返回固定格式"。这避免了判定偏差污染证据——子代理不会因为"觉得这像 bug"就下结论，只返回"第 X 行写了什么、第 Y 行读了什么"的原始事实。

判定由主审统一做，好处是**判定标准一致**。如果让多个子代理各自判定，会出现"甲代理觉得是 bug，乙代理觉得不是"的标准漂移。

**学习价值**：取证和判定要分离。取证可以并行、可以外包给对代码不熟的人（只要按固定格式返回事实）；判定必须集中、必须由理解全局的人做。

### 1.5 死 FLAG 发现能力，系统清理技术债

跨纪元 FLAG 生命周期表把所有 FLAG 的"写入点"和"读取点"做了一张全表，一眼就能看出哪些 FLAG"有写入无读取"。本次发现了 28 个死 FLAG，分布在 events.json、randomevents.json、GameEventManager.ts、GameFlags.ts 多个位置。

这种发现很难靠单文件审查做到——你必须把所有写入和所有读取对齐才能发现"写了但没人读"。死 FLAG 本身不导致崩溃，但它是技术债的强信号：说明这些代码路径要么是遗留废弃，要么是从未接通的半成品。

**学习价值**：技术债清理需要"全局对账"视角。单文件 review 永远发现不了死 FLAG，因为它在每个文件里都"看起来正常"。

### 1.6 四阶段渐进 + 明确完成标准，防止跳跃式结论

BASELINE 阶段的完成标准是"6 项要求全做完，但不下任何缺陷结论"；MODEL 阶段是"建审计模型骨架"；EVIDENCE 阶段是"取证"；CAUSAL_VALIDATION 是"因果验证"；REPORT 才是"正式问题"。

这种渐进式很重要。如果一上来就写"审计报告"，审计者会带着"我要找 bug"的预设去读代码，容易把正常设计误判为 bug。先建模型、先取证、先验证，最后才下结论，能减少预设偏差。

**学习价值**：审计要分阶段，且每个阶段有"不该做什么"的约束。基线阶段不该下结论，取证阶段不该判定，验证阶段不该修复。混淆阶段会降低质量。

### 1.7 修复可追溯，回归测试锁定成果

每个 FIX 对应具体的 AR/SYS 编号，修复汇报文档明确列出根因、修改内容、验证方式。更关键的是 FIX-17 新增了 19 个回归测试覆盖 FIX-01~FIX-13。

这保证了审计成果不会因为后续迭代而回退。比如 FIX-01 修正的 epoch 标注，如果未来有人误改回去，回归测试会立即失败。

**学习价值**：审计不结束于"发现问题"，也不结束于"修复问题"，而结束于"用测试锁定修复"。没有回归测试的审计成果是易碎的。

### 1.8 文档即知识沉淀，适合学习型项目

本项目定位为同人学习作品，文档本身就是交付物。27 份审计文档完整记录了"怎么从代码里推断出设计意图、怎么定位断裂点、怎么修复"，对独立开发者而言是高价值的学习材料——它记录的不是"答案"，而是"推理过程"。

## 二、缺点

### 2.1 文档膨胀严重，检索与维护成本高

27 份文档 / 单次审计，这个产出量带来了实际问题：
- **检索困难**：本次甚至需要专门新建文件夹把它们归档到一起，否则在 02_Project_Documentation/ 里和其他文档混在一起难以查找。
- **内容重复**：同一问题（如 AR-1）在 EVIDENCE、CAUSAL_VALIDATION、AUDIT_REPORT、CROSS_EPOCH_AUDIT、FIX_PLAN、FIX_EXECUTION 里被反复提及，每份文档都从自己的角度描述一遍，信息密度被稀释。
- **维护负担**：代码迭代后，这些文档会快速过时。本次靠"活文档"机制（SPEC、状态看板）做锚点更新，但 27 份取证文档本身没有自动更新机制。

**学习价值**：审计文档的"完整可追溯"和"精简可维护"是矛盾的。本次偏向了前者，适合学习型项目，但在商业项目里这种产出量会成为负担。

### 2.2 静态分析局限，大量"未确认项"无法闭环

本次审计本质是静态代码分析 + 人工因果推理。大量问题被标为"未确认（UC）"或"有证据支持"而非"已确认"，因为它们依赖运行时状态。

- UC-1~UC-18 共 18 项未确认问题，全部标注"待 Autoplay500 运行时验证"。
- AR-37（无逃逸技术玩家进入二向箔打击是否立即 DEFEAT）这种问题，静态分析只能给出"条件风险"，无法确认实际是否触发。

静态因果链分析能发现"路径上有个坑"，但确认"这个坑会不会被踩到"需要动态验证。本次审计的动态验证（Autoplay500）只覆盖了部分场景。

**学习价值**：静态审计的上限是"发现潜在问题"，不是"确认所有问题"。要配运行时验证（长时自动运行、断言、覆盖率）才能闭环。

### 2.3 人工因果链追踪易遗漏，依赖主审理解深度

本次审计最严重的架构缺陷之一——SYS-3（filteredEvent 的 `isEventCharactersUnlocked` 检查 `dialogNodes` 但实际使用 `dialogQueue`，且 `getFilteredEventsForTurn` 根本不调用该检查）——在历史多轮审计中都没被发现，直到这次跨纪元审计才暴露。

这说明人工因果链追踪有盲区：**审计者只能追他能想到的链路**。如果审计者没想到"filteredEvent 的人物检查可能走错属性"，就永远不会去验证这一条。这种盲区和代码规模正相关——Game.ts 1700 行、GameEventManager.ts 1132 行，任何人都无法全量保持心智模型。

**学习价值**：人工审计对"没想到的问题"无能为力。需要配合自动化检查（类型系统、lint 规则、契约测试）来覆盖盲区。

### 2.4 修复副作用难以完全预见

FIX-01 修正了 4 个事件的 epoch 标注（GOLDEN → CRISIS），这是正确的修复。但副作用是：这些事件的 `inYear <= 0`（如 year=-58），改成 CRISIS 纪元后会在 year=0 触发，作为交互事件阻塞了年份推进，导致 `Civilization.test.ts` 的 `runARound` 测试失败（`expect(game.year).toBe(1)` 得到 0）。

这个副作用在修复时没被预见到，是跑测试才暴露的。说明**审计修复本身也有因果链**，改一个标注会影响事件触发时序、影响测试、影响 AI 托管逻辑。本次靠"改完立刻跑全量测试"兜底，但不是所有副作用都能被现有测试覆盖。

**学习价值**：审计修复不是"找到错→改对"那么简单。每个修复都是一次小重构，要预期它有副作用，并用测试网兜底。

### 2.5 跨纪元继承问题重复登记，信息冗余

AR-20（BUNKER 断裂）在 BUNKER、GALAXY、STARDUST 三个纪元的报告里都被登记为"继承断裂"。跨纪元总审计又汇总一遍。这是为了"每个纪元报告自包含"，但导致同一问题在 4 份文档里出现 4 次，且每次描述略有差异（cycle= 后面跟的纪元链不同）。

**学习价值**：跨纪元问题和单纪元问题的登记方式应该区分。跨纪元问题应该在跨纪元层集中登记，单纪元报告只引用编号，不重复描述。

### 2.6 缺乏自动化支撑，规模大时效率低

本次审计全靠人工读码 + 子代理取证，没有静态分析工具链。比如"死 FLAG 发现"靠的是人工把所有写入和读取对齐成表——这个工作理论上可以用脚本自动化（扫描所有 addFlag/hasFlag 调用，输出无读取的 FLAG），但本次是纯手工。

当项目规模继续增长（事件数从 57→200、FLAG 从 40→100），纯人工审计的效率会急剧下降。本次审计单纪元就要产出 4 份文档，6 个纪元 + 跨纪元 = 27 份，这个工作量在商业项目里几乎不可持续。

**学习价值**：审计方法论要配合工具链演进。死 FLAG 检测、未读取字段检测、因果链可达性分析，这些都可以半自动化。

### 2.7 "数字漂移"暴露审计本身也需被审计

项目记忆里记录了一个元问题："文档系统存在数字漂移，声称的指标（结局数、行星数）与代码实现冲突"。本次审计也遇到了：endingConfig 注释写"6 胜 + 3 败"，实际是 6+4+2=12。

这说明审计文档本身也可能漂移。本次审计没有对"审计文档自身准确性"做校验——比如，AUDIT_REPORT 里声称"某 FLAG 在第 X 行写入"，这个声称是否准确？没有二次校验机制。

**学习价值**：审计有"元审计"需求。审计文档的每一条断言都应该可点击跳转到代码锚点，否则断言本身可能漂移。

### 2.8 过时风险高，依赖活文档机制兜底

审计文档的"证据截止"是 2026-07-12。一旦代码迭代，文档就变成"历史快照"。本次靠三个活文档（SPEC 核心系统权威、项目状态看板、项目记忆）做持续更新，但 27 份取证文档本身是静态的。

如果三个月后有人翻这些文档，他需要先判断"这些结论还有效吗"——而这个判断本身又需要一次审计。审计文档的"保鲜期"没有被显式管理。

**学习价值**：审计文档要标注过期策略。要么标注"证据截止日期，后续以代码为准"，要么接入活文档更新机制。不能让静态审计文档假装自己一直有效。

## 四、改进建议

### 4.1 短期（下一次审计可立即采用）

1. **合并 EVIDENCE 与 CAUSAL_VALIDATION**：两阶段内容高度重叠，可合并为"取证与验证"单阶段，减少文档数量。
2. **跨纪元问题集中登记**：在 CROSS_EPOCH_AUDIT 层集中登记跨纪元问题，单纪元报告只引用编号 + 一句话摘要，不重复完整描述。
3. **引入"审计断言"格式**：每条结论用 `ASSERT(文件:行号, 断言内容)` 格式，便于后续自动化校验。
4. **标注证据保鲜期**：每份文档头部加"证据截止日期 + 过期策略"。

### 4.2 中期（需工具链支持）

1. **死 FLAG 自动检测脚本**：扫描所有 addFlag/hasFlag 调用，输出"有写入无读取"清单，替代人工对账。
2. **因果链可达性可视化**：基于 FLAG 依赖关系自动生成纪元可达性图，替代手工画状态流图。
3. **审计文档版本化**：每份文档绑定 git commit hash，文档与代码版本一一对应。

### 4.3 长期（方法论演进）

1. **运行时验证层**：将 UC（未确认项）接入 Autoplay500 长时运行 + 断言，自动闭环动态问题。
2. **元审计机制**：对审计文档自身做抽样校验，确认"声称的代码锚点"与实际代码一致。
3. **分级文档策略**：核心结论进活文档（SPEC），取证细节进归档（本文件夹），不再维护"半静态半活跃"的中间态文档。

## 五、结论

这套"纪元级因果链审计"方法论的**核心价值在于视角**——它把代码当成状态流动的系统来审计，而不是当成静态文本扫描。这个视角让它能发现传统 bug 审计漏掉的级联失效和跨模块断裂，在本次审计中一次性清理了 28 个死 FLAG 和 7 项系统性问题，是历史任何单轮审计都没达到的深度。

它的**核心短板在于成本**——纯人工、文档膨胀、静态分析无法闭环动态问题。这些短板在商业项目里会致命，但在学习型项目里是可接受的代价，因为完整的推理过程本身就是交付物。

对独立游戏开发者而言，这套方法最大的学习收益不是"发现了多少 bug"，而是**示范了如何系统地理解一个复杂代码库**：先建基线摸清全貌，再沿因果链逐模块追踪，最后跨模块对账。这种系统化理解能力，比任何单次审计的结论都更值得带走。
